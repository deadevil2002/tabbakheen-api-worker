# Order participant, safety-report and cash-funding backend handoff

Branch `feat/tabbakheen-participant-safety-20261014` is a local/Draft-PR candidate based on `3681e9624285f7c0df6f5dfe626eddf6d5995871`. It is **not deployed**. Mobile must not depend on it in a released build until the Worker is separately approved and deployed.

## Mobile participant contract

`GET /orders/{orderId}/participant-summary` with `Authorization: Bearer <Firebase ID token>`. No request body or caller-supplied UID. Only the provider owning the authoritative order may use it, including while the order is pending. Response 200:

```json
{
  "success": true,
  "orderId": "order-id",
  "customer": { "displayName": "Customer", "avatarUrl": null },
  "driver": null
}
```

After an actual `orders/{orderId}.driverUid` assignment, `driver` is `{ "displayName": "Driver", "avatarUrl": null, "ratingAverage": 4.5, "ratingCount": 8 }`. Rating comes from the existing driver public-profile projection; there are no customer ratings. The current source has **no approved-avatar workflow or approved customer-avatar source**, so both avatar fields deliberately remain `null`; do not display an unapproved fallback image. Adding non-null avatars requires a separately verified approval source. A missing/deleting/disabled/suspended customer returns 409; a missing/deleting/disabled/suspended driver is omitted. Invalid role returns 403, wrong order returns 404, missing/invalid Firebase token returns 401. Only the listed DTO fields are returned—never phone, email, precise location, address, UID or a private profile.

## Existing complaint extension

`POST /complaints/create` accepts the existing 1.0.6/1.0.7 shapes unchanged. New safety form: `{ "orderId": "...", "type": "participant_safety", "reasonCode": "customer_received_unpaid|customer_no_show|abuse_or_threats|suspected_fraud|assigned_driver_problem|other", "target": "customer|provider|driver", "note": "10–500 characters" }`. The server derives reporter and target from Firebase auth and the order. `customer_received_unpaid` is provider-to-customer; `customer_no_show` is provider/driver-to-customer; `assigned_driver_problem` requires a currently assigned driver and a customer/provider reporter. The other reasons require another order participant. The same reporter can create only one safety report per order/target; exact retry is idempotent, changed content returns 409. Reports remain allowed after completed orders. No evidence-upload URL is accepted because no authorized private evidence flow was verified.

The reporter can retrieve status/history with existing `GET /complaints/mine`; it returns an allowlisted DTO without internal findings, target UID or risk counts. The reported participant discovers reports addressed to them through `GET /orders/{orderId}/complaints/received` with their Firebase ID token. This order-scoped endpoint derives at most two report IDs from the authoritative order's other participants; it does not scan complaints or accept a reporter UID. Response 200 is `{ "success": true, "orderId": "...", "complaints": [{ "id": "...", "orderId": "...", "source": "provider", "reasonCode": "...", "note": "...", "complaintStatus": "pending", "createdAt": "...", "hasResponded": false }] }`. Only reports whose stored target UID/role and reporter UID/role still match the order are returned. An authenticated unrelated account receives 404; unauthenticated access receives 401; deleting/suspended accounts cannot read. The response excludes all UIDs, Admin notes/findings, internal risk counts, other reports, order destination and private account fields.

The reported participant can then submit one authenticated response through `POST /complaints/{complaintId}/respond` with `{ "response": "10–1000 characters" }`; identical retry is idempotent, a changed response returns 409. `hasResponded` becomes true after success. Admin can see the response and use the existing complaint status/admin reply workflow. Safety report records omit the legacy `customerUid`, `providerUid` and `driverUid` fields so the current Bridge Rules' direct participant-read clause cannot expose private review data. The Final Rules deny direct client complaint reads as previously tested. New Admin review findings and aggregate cards are available only under the existing signed Admin API/session; no automatic account restriction is performed.

## Existing ratings and payment gap

`POST /ratings/submit` remains customer-to-provider or customer-to-assigned-driver only after `delivered`/`completed`, with a deterministic order/rating document, atomic average/count update and idempotent retry. This patch makes an exact retry reattempt a failed public-profile projection; a first committed rating no longer returns an HTTP failure solely because its best-effort projection read failed. A persistently failing projection remains an operational risk; this task does not change rating policy or schema. No customer-rating API was added.

For **legacy** cash/COD orders, delivery/self-pickup confirmation still marks `paymentStatus=PAID_CONFIRMED` without an independent cash-collection event. That historical behavior was not migrated. The new, explicitly opted-in V1 mode below instead separates provider receipt, driver-reported collection and customer acknowledgment; none automatically changes the legacy payment status field.

## Driver-funded cash delivery V1 — source-only, OFF

This follow-up adds a **new opt-in contract**, not a migration of existing cash orders. `CASH_FUNDING_V1_ENABLED` is exact-string `"true"` only and is absent by default. Per the owner's final policy, **there is no Admin or platform per-order cash-advance ceiling**: the driver chooses each order after reading the exact terms. The PR-only `cashFundingV1.maxDriverAdvanceSar` setting and Admin UI are retired; an old stored value is ignored, new Admin writes to that key return 400, and no stored production data is deleted or migrated. Existing offer-price validation, exact SAR cents, quote/pricing checks and safe-integer overflow protection remain. Existing `/orders/create` and normal `/orders/create-v2` payloads/behavior are unchanged.

1. A supported new customer client opts in only at `POST /orders/create-v2` by adding `"cashFundingVersion":1` to the existing request, with `paymentMethod:"cash"` (canonical `CASH`). The request ID and idempotency hash include the mode; old-client requests do not. The order stores `cashFundingIntentVersion:1`, not a funded delivery yet. A funded order is established only when the same customer calls existing `POST /finalize-delivery-v2` with `deliveryPaymentMethod:"cod"`, an eligible quote and an authoritative valid SAR amount. The legacy `/finalize-delivery` route rejects an opted-in order, including self-pickup, rather than silently discarding its consent contract; the customer must use the explicit V2 flow or cancel/recreate the order. Prepaid food, self-pickup, `arrange_with_driver` and non-opted orders never enter this mode. The existing finalization response shape is unchanged.
2. The driver sees the order ID in the **unchanged** `/deliveries/available-v2` DTO, then MUST call `GET /orders/{orderId}/delivery-classification-v1` with a Firebase ID token **before acceptance**. An eligible available driver gets exactly `{ "success":true, "contractVersion":1, "orderId":"...", "kind":"funded_cash_v1|ordinary_cod|other", "acceptanceEnabled":true|false }`; 404 means no longer eligible/available. `funded_cash_v1` is never inferred from a 404 on another route. If funded and enabled, read `GET /orders/{orderId}/cash-funding-v1` before accepting. For an eligible available driver it returns only `{ "success":true, "contractVersion":1, "orderId":"...", "foodAdvanceSar":25.5, "deliveryFeeSar":7.25, "customerCashTotalSar":32.75, "currency":"SAR", "platformDeliveryCommissionSar":0, "financialRiskNotice":{"code":"DRIVER_ADVANCES_OWN_CASH_V1","ar":"...","en":"..."}, "providerReceiptAcknowledged":false, "driverCollectionReported":false, "customerCollectionAcknowledged":false, "termsVersion":"...", "onHold":false, "deliveryStateVersion":2, "driverReleasedNoAdvance":false, "providerAttestedNoReceipt":false }`. Amounts are examples, **not a platform limit**. The UI must display all three authoritative amounts and the full localized risk notice before an affirmative driver action; it must not auto-accept. No customer address, GPS, contact, payment credentials or account UID is returned. After assignment, only order participants may read the same endpoint as an allowlisted status DTO. An old client's `/delivery-transition` `accept` cannot assign a funded order.
3. The new driver sends `POST /orders/{orderId}/cash-funding-v1/accept` with `{ "termsVersion":"<exact GET value>", "consent":true }`. An atomic Firestore read-write transaction checks the authoritative order ID/state/quote/pricing/amounts and risk-notice version, unassigned state, driver availability/entitlement/location/distance, all three participants' deletion requests and irreversible markers, and unique outbox/consent audit IDs. It atomically assigns the driver and stores a timestamped amount-specific consent. A stale terms/order/assignment change returns 409; disabled feature returns 503. Exact retry is idempotent. Uncertain commit is reconciled from order plus durable event and audit, never blindly resent. The existing bounded outbox/Cron dispatches assignment notifications.
4. The provider independently confirms **actual receipt of the food advance** with `POST /orders/{orderId}/cash-funding-v1/provider-receipt`, body `{ "termsVersion":"...", "amountSar":25.5, "currency":"SAR", "acknowledged":true }`. `picked_up` is blocked until that authenticated, audited receipt exists. A driver claim alone is not receipt proof. A funded-order driver **cannot use legacy `reject` after acceptance**; the explicit no-advance release contract below applies before payment, and paid/uncertain cases require manual review.
5. After arrival/handover, the assigned driver may report customer collection with `POST /orders/{orderId}/cash-funding-v1/collection-report`, body `{ "termsVersion":"...", "amountSar":32.75, "currency":"SAR", "reportedCollected":true }`. This is explicitly only **driver-reported**, not verified. The customer may then independently acknowledge with `POST /orders/{orderId}/cash-funding-v1/customer-ack`, body `{ "termsVersion":"...", "amountSar":32.75, "currency":"SAR", "acknowledged":true }`. Each event is one-time, actor-bound, idempotent and stored with a separate immutable audit document. `paymentStatus` remains unchanged by delivery handover, either collection button, or customer acknowledgment in this V1 mode; do not show `PAID_CONFIRMED` as proof of collected cash. `driverGrossDeliveryEarnings` remains the existing delivery fee; platform delivery commission remains zero. No wallet, payout, reimbursement or deduction is created.
6. `POST /orders/{orderId}/cash-funding-v1/issue` accepts only `{ "kind":"provider_refusal|customer_no_show|dispute" }` from an authorized order participant (provider-only refusal, driver-only no-show). One Firestore transaction records the audit, hold and exactly one deterministic `cash_funding_issue` case in existing `delivery_complaints`. The case is pending in the authenticated Admin complaint list and contains only the order ID, reporter UID/role, issue code and timestamps; it contains no order destination, contact, payment details or participant narrative. An exact retry creates no second case; an uncertain commit is reconciled against all three records. The hold blocks pickup, collection and further legacy delivery-state transitions; no automatic refund, penalty, reimbursement or re-assignment occurs.

### Exact Mobile PR #15 recovery contract

These are **new opt-in screens**, not changes to 1.0.6/1.0.7 DTOs. All new routes use Firebase ID-token authentication, server-derived participant identities, one-time immutable `order_cash_funding_events` audit IDs, atomic order CAS and deletion-marker fences. A successful POST returns `{ "success":true, "orderId":"...", "state":"<action>" }`, with `idempotent:true` on an exact retry. A stale/unsafe transition returns 409 (`stale_terms`, `state_conflict`, `manual_review_required`, `transition_not_allowed` or `event_exists`); an uncertain commit returns 503 `state_uncertain` and the client must refresh before retrying. No route automatically moves cash, releases a paid driver or converts an order.

- Customer, **no assigned driver**: refresh the funded-order view to obtain `deliveryStateVersion`, then explicitly POST `/orders/{orderId}/cash-funding-v1/convert-self-pickup` with `{ "expectedDeliveryStateVersion":2, "confirmSelfPickup":true }`. Never use legacy `cancel_driver_search` for a funded order. The atomic conversion ends driver matching eligibility, clears assignment, emits one durable `self_pickup_selected` outbox event, deletes the private delivery destination and sets delivery fee/driver earnings to zero and total to the exact food `priceSnapshot`. The funding/audit marker remains; no payment is confirmed.
- Customer, **assigned but unpaid**: the assigned driver first explicitly POSTs `/orders/{orderId}/cash-funding-v1/release-no-advance` with `{ "termsVersion":"<accepted exact terms>", "noAdvanceAttested":true }`. This irrevocably ends the driver's delivery-transition rights; assignment remains as evidence until the customer converts. The provider must independently POST `/orders/{orderId}/cash-funding-v1/provider-no-receipt` with `{ "termsVersion":"<same terms>", "noCashReceived":true }`. Only after **both affirmative attestations**, no conflicting receipt/audit/hold and an unchanged order version may the customer call the conversion route above. Missing provider acknowledgment alone is **never** no-payment proof. The driver/provider may inspect boolean `driverReleasedNoAdvance` and `providerAttestedNoReceipt` in the participant GET. If either party cannot attest truthfully, stop and request manual review; do not force conversion.
- **Paid or uncertain funding**: no release, rejection, cancellation, reassignment or self-pickup conversion. An authenticated `provider-receipt` after a driver no-advance release is retained as contradictory evidence and atomically creates one Admin complaint case and email-alert job with the manual-review hold. `POST .../issue` with `{ "kind":"dispute" }` does the same. Never infer payment from an absent receipt.
- **Converted self-pickup**: participant `GET /orders/{orderId}/cash-funding-v1` returns `{ "success":true, "contractVersion":1, "orderId":"...", "recoveryState":"self_pickup", "foodAmountSar":25.5, "currency":"SAR", "providerSelfPickupReceiptAcknowledged":false, "paymentStatus":"PENDING" }`. Existing `complete_self_pickup` may confirm food handover but **must not confirm cash**. Only the provider's explicit `POST /orders/{orderId}/cash-funding-v1/self-pickup-receipt` with `{ "amountSar":25.5, "currency":"SAR", "acknowledged":true }` records food-only cash receipt and changes payment status to `PAID_CONFIRMED`. Until then the obligation blocks account deletion, even after handover. An exact retry is idempotent.
- **Operational fallback** when a participant's one allowed complaint narrative for the same order/target is already used: place the order on hold through the existing authenticated `/issue` dispute route if not already held. The resulting case appears in the existing authenticated Admin complaint list without consuming another participant narrative slot. Mobile PR #15 must remove its current wording that tells users to submit this complaint through support email/WhatsApp; those contacts are for ordinary support only, never automatic complaint forwarding or an alternate complaint inbox. The participant may view the existing case through the normal complaint history where applicable. Admin handles resolution manually; no second complaint slot, private findings or financial transition is exposed.

**Owner-approved Admin email alerts — existing backend deployed; Arabic template update local only:** the owner explicitly approved the existing Admin `app_settings/main.supportEmail` as the recipient. Every new Worker-created legacy, participant-safety, chat or funded-cash complaint atomically creates one metadata-only `complaint_email_alerts` job in the same Firestore commit. An exact request retry does not create another job; status updates, reads and participant responses do not enqueue email. One bounded Cron unit reads the current validated Support Email at its first send attempt, freezes the recipient and minimal payload for idempotent Resend retries, and links to authenticated `/admin#complaints`. A later Admin Support Email change is used by all subsequently first-attempted jobs without redeployment; an already attempted job keeps its frozen recipient/payload so a retry cannot accidentally send a second, different email. Missing/invalid recipient or sender credentials preserves the complaint and records a retryable failure without inventing a fallback. Transport failures retry with bounded leases/CAS, at most five sends and one stable Resend idempotency key per case. An unresolved/uncertain alert is marked `needs_review` before Resend's 24-hour idempotency window expires; it is **not** blindly resent afterward. Provider acceptance is not proof of mailbox delivery, and exactly-once delivery is not claimed. The proposed new Arabic RTL HTML template uses an orange Tabbakheen header, Arabic subject/category, Gregorian submission time in `Asia/Riyadh`, compact references and an authenticated Admin link; it is generated only for not-yet-frozen jobs. Already frozen or sent jobs retain their payload and are not resent. No full narrative, private destination, contact, financial data or WhatsApp forwarding is included. Existing transactional emails remain unchanged. Production Rules were not freshly verified in this task; do not infer their current state from local tests.

**Optional Saudi Short Address (local backend contract for Mobile 1.0.7):** authenticated customer `POST /customers/delivery-location` accepts the existing six fields plus optional `shortAddress` matching exactly `^[A-Z]{4}[0-9]{4}$` (example `ENAB2500`); authenticated customer `GET` and successful `POST` return it only when valid/present. Requests without it, including 1.0.6, retain the old response shape and replace the saved preference without a short address. This is format validation, **not SPL verification** or automatic code generation. It is stored only in the private customer delivery preference. `POST /delivery-quote-v2` remains unchanged; `saveAsDefault` preserves the code only if the quoted address is identical to the saved address, otherwise clears it. No code is copied into orders, public discovery, notification payloads or the assigned-driver delivery-details DTO. If Mobile needs driver-visible Short Address for a specific order, it needs a separately coordinated, order-private quote/finalization and assigned-driver DTO extension before use; do not infer that saved preferences alone implement that handoff. No external SPL integration or credential is included.

Classification is a narrow order-scoped read, not an expanded `/deliveries/available-v2` DTO. It returns only a mode label and acceptance flag; `ordinary_cod` continues through the existing legacy path, `funded_cash_v1` requires amount-specific V1 consent, and `other` follows its existing delivery contract. `CASH_FUNDING_V1_ENABLED` remains OFF by default. Existing 1.0.6/1.0.7 clients and legacy self-pickup remain unchanged. Pending old match notifications can be stale after a conversion; every new acceptance checks the authoritative order, and the client must refetch before showing an actionable order.

All cash-funding writes use documented Firestore REST transaction Writes, bounded retries and missing-marker reads. Common errors are `INVALID_REQUEST` (400), `UNAUTHORIZED` (401), `FORBIDDEN`/`NOT_FOUND` (403/404), `CASH_FUNDING_DISABLED` (503), `CASH_FUNDING_INELIGIBLE`, `CASH_FUNDING_INVALID_AMOUNT`, `ORDER_PRICE_INVALID`, `STALE_TERMS`, `EVENT_EXISTS`, `ACCOUNT_DELETION_BLOCKED`, `TRANSITION_NOT_ALLOWED` (409), and `STATE_UNCERTAIN` (503). `CASH_FUNDING_LIMIT` is retired. The existing `paymentStatus` meaning for legacy orders and their routes remains unchanged. Disabling the funding flag blocks new opt-in creation/assignment; already assigned funded orders can still complete receipt/collection and safe delivery transitions.

**Activation gates:** separately approved Worker flag; Mobile PR #15 customer/driver/provider recovery screens and versioned classification, exact DTO/risk-notice parsing and truthful no-advance/no-receipt attestations; coordinated Final Firestore Rules that deny direct client order/audit writes; configured manual-support contact; offline emulator/security and real-device QA; explicit owner activation. Production still has Bridge Rules and this PR is not deployed, so none of those gates are asserted as complete. Old 1.0.6/1.0.7 driver clients may see a funded order in their unchanged V2 availability list but cannot accept it; do not activate until the supported driver UI is available. No Admin-maximum prerequisite exists. Human developer owns merge/activation/release; no production data, credentials or real cash moved in these tests.
